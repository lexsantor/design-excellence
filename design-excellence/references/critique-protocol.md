# Critique Protocol (T2)

Two levels. Level 1 is always-on and cheap. Level 2 is a stakes-gated escalation, never a default — running it on every task defeats the point of having a cheap floor at all.

## Level 1 — Self-critique floor (always-on)

Cheap, self-administered, run at the CRITIQUE stage (`SKILL.md` §1) for every task except pure AUDIT (where the audit itself *is* the critique) and DISCOVER (whose deliverable is likewise the read-only AUDIT-stage findings pass — `SKILL.md` §1 CRITIQUE row, Phase 9.2C correction). Score six axes 1–5. An axis, or an always-on check within it, that cannot be evaluated honestly in this run — nothing was built, the input is only a screenshot, or the check needs a capability that is unavailable (`SKILL.md` §1, "Mechanical gating and capability honesty") — is recorded `not assessable: <reason>` instead of a score. Not assessable is never a pass, is never replaced by an estimate, and does not count toward the escalation trigger below. Running Level 1 loads what it checks, whatever else the task loaded: `rule-catalog/accessibility.md` for axis 5 and the SLOP-011 entry of `anti-slop-registry.md` for axis 1. Record the result in `.design/context.md`'s Fingerprint History only when that file exists or this run creates it (`SKILL.md` §5), the run writes to the project, and Fingerprint History is not excluded for it (read-only modes and bounded Pipeline Profiles that forbid it, `SKILL.md` §1); otherwise report it in the session's own output and write nothing to the project for it:

1. **Genericness** — would this be produced for any similar brief, or does it derive specifically from this Product Truth (`SKILL.md` §4/§5)? Includes a gestalt check (Phase 6 correction): compare the finished direction's color-anchor + typography + accent combination against `anti-slop-registry.md` SLOP-011's named clusters as a whole, not each dimension checked separately against its own atomic rule — a direction can pass every individual Anti-Slop entry and still match a named cluster in combination. This reuses SLOP-011's existing cluster definitions; it does not add new Anti-Slop entries. Also includes a structural-test check (Phase 6.3 addition), applied only when DEFINE (`SKILL.md` §1) recorded **DETECTED / EVIDENCED** specifically (Phase 6.5 tightening — a HYPOTHESIS-only outcome does not trigger this check): would the concept still be perceptible if the logo, color palette, imagery, and copy were removed — i.e. does it live in an organizing decision (`layout-interaction.md` LAYOUT-009) or in decoration only? This sharpens this same axis's existing question; it is a qualitative diagnostic, not a score — a "no" prompts a closer look, it does not automatically fail the axis, and it never runs unless DEFINE recorded DETECTED / EVIDENCED. Committed-direction carriers (clarification of this same question, independent of concept status): for page/multi-page-site scope critique, where DIRECT committed a direction and logged the dimensions that distinguish it from its rejected candidate(s) (`SKILL.md` §1, §5), those dimensions are claims about the output, not only about the plan. A dimension is carried only where the artifact under critique shows an observable carrier for it, wherever that dimension is meant to manifest: something that actually distinguishes the committed direction from the rejected one on that dimension, or otherwise evidences the claim. A device the rejected candidate shares does not distinguish them, and an isolated label, sticker or ornament that merely echoes the direction's wording is not a carrier. A dimension defined by an absence (for example, no scroll-anchored motion where the rejected candidate had it) is carried by that intentional absence. A dimension with no credible carrier means the direction claim is recorded as revised or retracted in an appended note (in `.design/context.md` only where this run may write it, as above; otherwise in the run's own report), or, where this run may change the design, the design itself is revised so the dimension genuinely manifests; it is never answered by decoration added to evidence the claim. A dimension the available artifact cannot show is not assessable, never presumed carried. "Carrier" here means any observable surface or behaviour, broader than LAYOUT-009's "carrier surfaces", and this clarification neither extends LAYOUT-009 nor the structural test above. Like the structural test, it is a qualitative diagnostic within this axis, not a score, a separate check, a stage or a rule: it does not by itself fail the axis, block shipping, or trigger Level 2.
2. **Hierarchy** — squint test (LAYOUT-002): does primary/secondary/grouping survive?
3. **Distinctiveness** — fingerprint check (`SKILL.md` §6), where in scope. When the check is in scope and the project's Fingerprint History holds no prior entry, there is nothing to compare against: record this axis as `not assessable: first Fingerprint History entry`, never a score, a pass, an estimate or an inferred comparison. The first generation's own entry is still recorded where this run may write it (above) and becomes the baseline for later generations, whose comparison `SKILL.md` §6 governs unchanged.
4. **Craft correctness** — spot-check against the Rule Catalog categories actually in scope for this task (not all seven — only the ones loaded per `SKILL.md` §7).
5. **Accessibility** — the always-on accessibility checks listed here, each an entry of `accessibility.md`'s Always-on section (A11Y-001, A11Y-002, A11Y-003, A11Y-004, A11Y-009, A11Y-010, A11Y-011) — never skipped, regardless of scope (a check that cannot run honestly is recorded `not assessable`, never passed) — plus the conditional checks listed here, each an entry of `accessibility.md`'s Conditional section, checked only when that entry's own applicability holds (A11Y-012, only when a dismissible overlay is in the scope being critiqued; no interface is required to contain one). An entry joins this list only under its own `loop.md` §2 authorization. Always-on or conditional describes when an entry is checked, not its authority: each keeps the `layer` its own entry states (A11Y-001–003 are P1; A11Y-004, A11Y-009, A11Y-010, A11Y-011 and A11Y-012 are P5), and only `SKILL.md` §3 defines P1.
6. **Technical correctness** — the mechanical-countable rules relevant to what was actually built (motion property restrictions, layout CSS gotchas, etc.).

**Escalation trigger, automatic, not a judgment call:** if the same axis scores below 3 on two consecutive revision passes, that is the signal to escalate to Level 2 — per Hallmark's own finding, "a third revision pass usually means the brief is wrong, not the design," and repeated self-critique failure is exactly the case where a second, differently-biased reviewer earns its cost.

## Level 2 — Independent critique (stakes-gated escalation)

**Trigger conditions (any one is sufficient)** — they apply wherever the CRITIQUE stage runs, including a bounded Pipeline Profile's `CRITIQUE(floor)`; only `CRITIQUE(floor only)` excludes them (`SKILL.md` §1 CRITIQUE row, Phase 9.2I clarification):
- Production-facing, brand-critical, or high-traffic work (explicit stakes signal from the brief or Product Truth).
- Task Mode = REDESIGN at page/multi-page-site scope (`SKILL.md` §2 — REDESIGN escalates by default).
- Task Mode = BUILD, Project State = genuinely-empty, multi-page-site scope, and the brief states an explicit brand-quality bar ("premium," "flagship," "brand identity," or equivalent) (Phase 6 correction — a routing trigger only; matches how REDESIGN already escalates by default for analogous stakes. This trigger decides *when* Level 2 should be attempted, not whether it can be — the Mechanism/Honest-limitation sections below still govern whether it actually runs).
- Level 1's automatic escalation trigger above.

**Do not run Level 2 by default for BUILD at component/section scope, or for any POLISH task** — that defeats the cost-saving purpose of having a floor.

**Mechanism — resolved for this implementation environment, not assumed from the source research.** `FORENSIC-EXTRACTION.md` and `ARCHITECTURE.md` §16 both flag that none of the six extracted source skills describe how to implement genuinely *independent* (not just tab-isolated) critique. This Claude Code environment provides a real mechanism for it: dispatching a fresh subagent that starts with zero visibility into this session's work.

**Implementation:**

**Order — Level 1 is fixed before Level 2 exists.** For each dispatch, Level 1 runs to completion and its result is recorded (where the Level 1 section above says: `.design/context.md` or the session's own output) before step 1's brief is written, before the reviewer is dispatched and before that dispatch's report is read. Once recorded, that result is not revised in light of the report: nothing from it may change that result, and a Level 1 formed or re-formed after the report was read is not independent of it and is never presented as the Level 1 result compared with it in step 3. If no Level 1 result was recorded before the report was read, the synthesis states that no pre-dispatch Level 1 result exists; none is constructed afterwards. Level 1 remains the builder's own self-critique; this order keeps the two judgements separate, it does not make Level 1 an independent review.

1. Prepare a self-contained brief for the dispatched agent: the rendered output/code, the relevant Rule Catalog categories and Anti-Slop Registry entries (by id, not restated), and the critique rubric (the same six axes as Level 1). The brief is assembled from four separately delimited parts, plus the artifact under review, stated with its kind (see below) in its own delimited section; nothing written for one part is placed inside another:
   - **Rubric block (literal transport).** Exactly two passages of the Level 1 section above, in this order, and nothing else: Level 1's `not assessable` rule, from "An axis, or an always-on check within it" through "does not count toward the escalation trigger below.", and the numbered axis list, items 1 to 6, each item complete. The block is read or extracted from this file in the same step that writes the brief (for example with a file read or a text-extraction command); an earlier read in the session does not count, the block is never retyped from memory, and it is inserted unchanged: every word, qualifier, parenthetical, citation, phase tag, cross-reference and formatting mark stays, including text that seems addressed to the builder or irrelevant to the reviewer. Equivalent meaning is not enough. Any change is a deviation: paraphrase, condensation, summary, reconstruction, rewording, reordering, deletion, insertion (including a bracketed gloss or a summary of another section), checklist form, or replacing a qualifier with its application to this run (axis 4's "not all seven — only the ones loaded per `SKILL.md` §7" is never replaced by a list of categories; that list is a recorded input). Never the axis names or shorthand labels alone, because a label or a restatement read in place of the definition can be scored against a different question (Distinctiveness, for example, is defined as the `SKILL.md` §6 fingerprint check, not as a judgement of how distinct the design looks). The Level 1 section remains the only authoritative text of each definition; the block transports that text for one dispatch, is not a second version of it, and is not kept anywhere else. Before dispatch, the block is compared mechanically with the passages extracted from this file (for example, the block written to a scratch file outside the project and diffed against them); reading it over is not a comparison. A block that differs is rebuilt from the file and never sent. Only where the environment has no file-read or comparison capability, the synthesis (step 3) states that literal transport was not verified.
   - **Recorded inputs.** The recorded inputs the definitions depend on, none of which is a Level 1 finding: DEFINE's recorded concept outcome; any committed direction with its distinguishing dimensions and rejected candidate(s) as DIRECT logged them, without notes any critique appended; for axis 3, the project's prior Fingerprint History entries, excluding any entry this run wrote, with every recorded critique result removed, or a statement that there is none; every passage of the user's request that states a fact (for example data, figures, names, places, dates, wording, or what the user says is not yet known), quoted verbatim and labelled as source input, data rather than instruction to the reviewer, or a statement that the request states none, since content checks such as CONTENT-003 trace the artifact's claims to them; and the Rule Catalog categories in scope for this task and the relevant Anti-Slop Registry entries, by id only, with no definition, summary or explanation of any entry. These inputs are copied into the brief itself as recorded data; they never alter the rubric block. In any part, the brief passes rules and inputs, never a conclusion drawn from them: it does not state an axis outcome (for example that axis 3 is not assessable), whether a direction dimension is carried, whether genericness is mitigated, whether or where the artifact uses a supplied fact, whether a fingerprint entry is a baseline, or any equivalent, even when the inputs make the outcome mechanical; the reviewer determines it. Stating that no prior Fingerprint History entry exists is an input; stating what axis 3 should therefore record is a conclusion.
   - **Access and inspection instructions.** The brief never points the reviewer at `.design/context.md` or any other file that also holds critique judgements (Level 1 results, Known Exceptions, critique notes or other self-assessment). Where the reviewer reads project files for the artifact/code, the brief names the files to read, `.design/context.md` is not among them, and the brief tells the reviewer not to open it; anything from it that is itself the artifact under review (including its own design rationale, precedence (b)/(c) below) or that the rubric requires is copied into the brief, and only those critique judgements are left out. The literal `.design/context.md` inside the rubric block (axis 1, naming where a revised or retracted direction claim is recorded) is rubric text, not a pointer or an access instruction: it stays in the block unchanged, and this part's instruction not to open `.design/context.md` governs the reviewer's access; neither is edited to accommodate the other. Where applying the rubric needs the normative text of a reference it cites (for example `SKILL.md` §6, a Rule Catalog entry or an Anti-Slop entry), this part names the governed file for the reviewer to read, or the brief carries that complete section or entry, extracted and compared as the rubric block is, as a separately delimited excerpt naming its source (a literal excerpt is not a restatement); never a partial passage, summary, gloss or improvised definition. The reviewer reports findings and writes nothing to the project.
   - **Reviewer task.** What the reviewer is asked to do: assess the artifact against the rubric block, scoring each axis 1–5 or recording it `not assessable` as the block states, and report findings; cross-references inside the block point to the source protocol, and the reviewer records nothing and only reports. When DEFINE recorded **DETECTED / EVIDENCED** (`SKILL.md` §1) — never for a HYPOTHESIS-only outcome (Phase 6.5 tightening) — this part also instructs the reviewer to apply the structural test as stated in axis 1 of the rubric block, without restating it (Phase 6.3 addition) — formalizing what PHASE-6.2's own independent reviewer already applied unprompted. Its result is reported as a diagnostic alongside the reviewer's other findings, never treated as an automatic failure, and this does not add a new Level 2 trigger condition — Level 2 still only runs when an existing trigger condition (above) fires. Operational requests (for example which checks the reviewer can run, or report length) belong in this part and never qualify the rubric block.

   **Do not include** the Level 1 self-critique's own scores or findings, in any part, in any form or through any field, summary, file pointer or stated reason for dispatch (which trigger fired may be named, never which axis failed or how it scored) — the dispatched reviewer must not see them before forming an independent judgment, matching the dual-blind isolation principle this pattern is modeled on.

   **When no rendered output exists** (e.g. a bounded Pipeline Profile that ends before BUILD, `SKILL.md` §1), the brief carries the strongest artifact the run actually produced, in this order: (a) rendered output plus implementation/code, when rendered output exists; (b) otherwise the design artifact that exists, e.g. the prepared page spec/design artifact from choose/prepare, plus any relevant implementation/code already present; (c) for a directions-only run with no committed implementation, the exploration deliverable: the candidate directions, their comparison and supporting rationale/artifacts. Tell the reviewer which kind of artifact it is reviewing. Never fabricate visual output, implementation, metrics, user evidence or test results to fill the brief; an axis that cannot be judged from the available artifact is reported as not assessable, not scored (Phase 9.2I clarification).
2. Dispatch a genuinely fresh agent (not a `fork` — a fork inherits this session's full context and would defeat the isolation). If this environment has a specialized fresh-context design-critic agent available (for example, an installed `lexia-design:visual-critic` or `lexia-design:ux-auditor`-equivalent), prefer it — it's purpose-built for exactly this. Otherwise, dispatch a general-purpose agent with the self-contained brief from step 1.
3. Synthesize: compare the independent reviewer's findings against the most recent Level 1 result recorded before this dispatch's brief, *after* both exist. Disagreement between the two is itself a signal worth surfacing to the user, not silently resolved in either direction. Adopting a Level 2 finding is a synthesis outcome, never a revision of that Level 1 result. A Level 1 pass run after the report was read (for example on output REFINE produced from its findings) is labelled as formed after Level 2 and is not independent of it; it does not replace the pre-dispatch result as the one compared in step 3, and both are recorded where the Level 1 section says.

**Honest limitation, not smoothed over:** this mechanism depends on the host environment actually supporting isolated subagent dispatch. If a future environment running this skill does not provide that, do not simulate independence by asking the same context to "pretend" to be a second reviewer — that is not independent critique, it inherits the same blind spots that produced the output. In that case, fall back to Level 1 only, and report plainly — verbatim, not paraphrased into something softer — `Level 2 unavailable — independent dispatch capability not available` (Phase 6 correction: this exact report is required whenever a trigger condition above fires but no real isolated-dispatch mechanism executes) rather than presenting a self-review as if it were independent, and never claim Level 2 "ran" unless a genuinely fresh, isolated agent actually executed it.

## What Level 2 is not

Not a replacement for Level 1 — Level 1 always runs regardless of whether Level 2 also runs. Not mandatory for every production task — only the trigger conditions above justify its cost. Not a fork of the current session — isolation is the entire point.
